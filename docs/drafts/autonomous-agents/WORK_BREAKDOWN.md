# 기능별 세부 작업·산출물·인터페이스

> 채택 전 작업 분해안이다. 현재 구현 진척과 관계없이 전체 개발 범위를 나눈다.
> A~E는 기능 영역이며 사람 이름이 아니다. 아래 20개 작업의 크기는 서로 다르다.
> 권한·보류·시간·재시작 정책은 [임시 설계 본문](DESIGN.md)을 따른다.

## 읽는 방법과 난이도

인터페이스의 T는 Topic, S는 Service, A는 Action이다. 지속 관측은 T, 짧은 요청·응답은
S, 진행 상태·취소가 필요한 장시간 실행은 A로 나눈다. 같은 기능을 세 방식으로 중복 구현하지 않는다.
아래의 상태·요청 이름은 계약의 의미를 나타낸다. 정확한 경로·타입·필드는 공통 계약에서 확정하며,
이 표가 새 ROS 인터페이스의 구현 완료를 뜻하지 않는다.

| 난이도 | 판단 기준 |
|---|---|
| 중 | 입력·출력과 실패 조건이 비교적 명확하며, 단일 모듈 중심으로 시험 가능 |
| 상 | 좌표·물리·인식·계획 또는 여러 노드의 비동기 처리를 함께 검증해야 함 |
| 최상 | 안전 우선순위, 취소 경합, 분산 상태·복구·영속성을 함께 다루며 통합 실패 영향이 큼 |

난이도는 개발·시험 복잡도의 상대 평가다. 소요일·인원 수의 환산값이 아니며,
모델 선정·데이터 품질·팀 숙련도가 정해진 뒤 일정으로 산정한다.
의존성은 통합 검증에 필요한 선행 결과다. 계약과 모의 입력이 있으면 구현은 병행할 수 있다.

## 공통 선행 작업 K0 — 계약과 시험 기준

20개 기능에 중복 계산하지 않는 공통 작업이다. 인터페이스별 생산자와 소비자가 함께 작성하고
해당 상태의 소유 영역이 최종 의미를 정한다. 향후 네 사람 배정 시 공통 작업의 담당도 명시한다.

| 산출물 | 포함 내용 |
|---|---|
| 인터페이스 명세·공유 타입 | 로봇·작업·물체·실행 ID, 단위·좌표계, Topic QoS·최신성, Service 오류, Action 취소·Result·Feedback |
| 권한·실행 계약 | 발신자 인증, 상태 소유권, 단계별 실행 ID, 예산·lease, 보류·재시작 규칙 |
| 모의 구성 | A~E 서버·상태 발행기, 정상·만료·단절·중복·취소 입력, 실제 실행과 구분되는 시험 데이터 |
| 검증 기준 | 시나리오별 성공·실패·판정 불가, 시뮬레이션/감독 시계, 독립 관측 로그와 재현 조건 |

공유 메시지 패키지의 도입·타입 확정도 이 범위다. 원장 형식이나 모든 임계값이 정해질 때까지
전체 구현을 기다리지는 않되, 서로 연결하는 계약은 소비자와 합의한 버전으로 고정한다.

A2의 공구 요청 수락은 집기 성공이 아니다. 실제 부착 상태를 A가 제공하고 C가 조작 결과를
판정한다. 최종 그룹 물체 상태는 D가 정한다. A4는 B4의 위험 판단을 구현하는 영역이 아니라
그 판단과 로컬 조건에 따라 실제 구동을 제한하는 영역이다.

| E2 로봇별 Agent | robot_1 조작·후보 선호와 robot_2 운송·대기 제안, 분리 문맥·권한·실패 처리. 자기 로봇 범위·오래된 상태 시험 | T: D의 로봇별 snapshot → 각 Agent별 제안 → D4. robot_1 후보 의견은 D→A→C 경로 | K0, E3, C3·D1·D2 상태 계약 | 상 — 두 Agent의 문맥·대상 분리와 기존 계획 주체 침범 방지 |
| E3 추론·도구·인증 연계 | 공용 추론 어댑터, 스키마·허용 도구, 발신자 식별·인증 연계, 출력 파싱·지연/오류 처리, 외부 전송 정책 | LLM API/로컬 서버 ↔ 어댑터. T: Agent별 인증된 제안·추론 상태 → D4. 내부 도구 호출은 제안 생성이며 직접 구동 아님 | K0, D4 수신·인증 계약, 모델/실행 방식 선택 | 상 — 발신자 사칭·스키마 오류·늦은 응답·서버 공유 |
| E4 Agent 평가·비교 하네스 | OFF/ASSISTED 효과 비교, ADVISORY 제안 품질, shadow 입력·출력 평가, 모델·프롬프트·스키마 버전 로그. 반복 실험·독립 관측 결과 | T/로그: A~D 실제 실행·제안·결과 수집. 시험 입력 → Agent 또는 격리 검증기. 실행 모드 변경은 검증된 관리 경로 | K0, E1~E3, D4. 실제 효과 비교에는 A~D 종단 시나리오 | 상 — LLM 비결정성과 환경 차이를 분리한 평가 |

D4가 실제 권한·제안 수락을 강제하고 E3는 그 계약에 맞춰 전달한다. E4의 하네스가
권한을 우회하지 않는다. D 검증기의 거절 사례는 D4의 계약 시험이며, E4는 Agent 출력 품질과
종단 비교를 맡는다. 인증 검증 전에는 실제 ASSISTED 운용 성공을 주장하지 않는다.

## 통합 순서와 의존 관계

| 단계 | 먼저 연결할 작업 | 이 단계의 확인 기준 |
|---|---|---|
| 1. 계약·모의 실행 | K0, A1. A3·A4·D2~D4·E3의 모의 개발 병행 | 단위·ID·상태 소유권·취소·오류 계약 합의, 모의와 실제 로그 구분 |
| 2. 로봇·관측·기본 동작 | A2·A4, B1~B4, C1·C2, D1 | 명령·상태·TF·관측 최신성, 위험 요구와 실제 정지 확인 |
| 3. 규칙 기반 조작·협업 | C3·C4·A3, D2·D3·D4 | 집기·적재·운송·하역, 인계 상호 배제, 통로·중복·복구 시험 |
| 4. Agent 기록·검증 | E1~E4, D4 인증·격리 | ADVISORY·shadow 품질, 잘못된 제안 거절, Agent 장애 시 규칙 실행 |
| 5. 제한적 자동 반영 | ASSISTED 연결, 전체 장애·비교 시험 | 인증 후 허용 판단 지점만 반영, 효과·복구·사람 확인 예외 측정 |

단계는 선행 조건이지 고정 주차가 아니다. 예를 들어 E의 프롬프트·스키마 시험은 기록된
snapshot으로 먼저 할 수 있지만, 실제 운반 효과 평가는 규칙 기반 경로와 독립 관측이 갖춰져야 한다.

## 네 사람에게 배정할 때의 기준

기능마다 4개로 나눈 것은 업무 경계를 드러내기 위한 것이며, 행 수가 같다고 공수가 같지는 않다.
특히 다음 작업은 내부 산출물 단위로 추가 분할해 배정량을 조정한다.

| 큰 작업 | 나눌 수 있는 내부 산출물 | 유지할 통합 책임 |
|---|---|---|
| A4 | 관절 보호 / 최종 구동 게이트·정지 확인 / 프로세스·시계 감독 | 정지 우선순위와 실제 구동 조건 |
| C4 | 조작 실행 / 보유·해제 결과 / lease·시도 보고·취소 | 물리 시도와 Action 결과의 일치 |
| D2 | 작업 배정 / 인계 단계 / 그룹 물체 상태·완료 | 그룹 단계 전이 |
| D4 | 인증·제안 검증 / 보류·격리 / 예산·실행 원장·복원 | 승인 권한·예산·영속 상태의 일관성 |

사람별로 상·최상 작업, 데이터·모델 작업, 인터페이스 구현, 통합 시험을 섞어 배정한다.
Topic·Service·Action 경험은 실제 담당 기능의 적절한 호출부·서버를 배정해 확보하며,
체험을 위해 불필요한 인터페이스를 추가하지 않는다. 개인별 담당과 기간은 아직 확정하지 않았다.

이 표의 완료 확인은 앞으로 수행할 검증 요구다. 현재 작업이 끝났거나 G1을 충족했다는 판정이 아니다.
