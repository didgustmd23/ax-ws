# A3 lease 지연 조사와 수정 — 2026-11-18

## 확인한 문제와 수정

보고된 p99 203ms의 원본 명령·실행 조건은 확보하지 못했습니다. 따라서 그 실행의 원인을 확정한 것은 아닙니다.

A3 시험에서 별도로 CPU·저장소 부하를 주자 p99 162.139ms, 162.525ms로 100ms 기준 초과를 재현했습니다. 조건은 Windows 마운트 경로의 원장, 시험 프로세스 CPU 1개 제한, 자체 CPU 부하 프로세스 4개, 동시 클라이언트 4개, 요청 1,000개입니다. 실제 Gazebo/D4 운영 시험이 아니라 dev_allow와 모의 Action 시험입니다.

기존 잠금에서는 오래 기다린 요청보다 나중 요청이 먼저 원장을 사용할 수 있었습니다. 가장 느린 요청은 잠금 대기 235.55ms, 자체 커밋 4.15ms였고, 뒤늦은 요청 15개가 먼저 처리됐습니다. 보수적인 시간 비교에서 두 회차 각각 399개·376개 대기 요청의 추월을 확인했습니다.

`fair_lock.py`의 FifoLock으로 원장 대기열에 들어온 순서대로 처리합니다. 이는 네트워크 도착 순서나 운영체제 실행 순서까지 보장하는 기능은 아닙니다. `lease_check.py`에서는 원장 잠금만 교체했습니다. SQLite WAL/FULL, 커밋 후 응답, 권한 검사, 멱등 규칙과 시험 합격 기준은 유지했습니다. 취소된 대기자는 제거하고, 예외가 발생해도 잠금을 해제합니다.

## 재검증 결과

| 조건 | p99 결과 |
|---|---|
| 수정 전 동일 부하 2회 | 162.139 / 162.525ms — 실패 |
| 수정 후 동일 부하 5회 | 83.122 / 98.794 / 90.897 / 87.086 / 85.623ms — 통과 |
| 수정 후 Linux 임시 저장소 2회 | 30.936 / 30.010ms — 통과 |

각 회차 1,000개 요청과 1,000개 수락 기록을 확인했습니다. 수정 후 부하 5회에서 분석으로 확인된 추월은 0개입니다. 관련 A3·회귀·스타일 검사 94개도 통과했습니다. 부하 조건에서는 중앙값이 늘어나는 비용이 있으며, 무제한 부하에서도 100ms를 보장한다는 의미는 아닙니다.

느린 요청별 구간 요약을 추가한 뒤 Linux 임시 저장소에서 다시 2회 측정한 결과는 p99 29.771 / 33.016ms였습니다. 추가 회귀 검사 22개와 스타일 검사 2개가 통과했습니다. 첫 회차 최장 요청은 전체 47.570ms 중 원장 대기 37.804ms, SQLite 처리 3.670ms, 나머지 서버 처리 0.133ms, 서버 밖 5.964ms였습니다. 이 실행에서는 원장 대기가 가장 큰 구간이지만 원본 203ms 실행의 원인 증거는 아닙니다. 결과는 `current_diagnostic/`에 저장했습니다.

## 다음 실패에서 원인을 확인하는 방법

WSL에서 ROS와 현재 설치본 환경을 불러온 뒤 저장소 루트에서 실행합니다.

```bash
python3 tools/tests/run_a3_latency_profile.py \
  --output docs/reports/a3_latency_new_run --rounds 2
```

각 round 폴더의 `summary.json`은 p99·최대 지연·원장 경로·CPU affinity·실제 SQLite 동기화 값을 기록합니다. `profile.json`의 `slowest_requests`는 **같은 요청**의 왕복 시간을 다음 구간으로 나눕니다.

- `ledger_wait`: 다른 요청이 원장을 쓰는 동안 기다린 시간
- `sqlite`: 트랜잭션 시작·조회·쓰기·커밋 등에 걸린 시간
- `other_inside_server`: 위 구간을 제외한 서버 내부 시간
- `outside_server`: 서버 계측 밖의 전송·콜백 진입·클라이언트 실행 대기 등이 합쳐진 시간

`largest_measured_part`는 가장 큰 측정 구간을 표시할 뿐 근본 원인을 자동 확정하지 않습니다. SQLite 구간에도 CPU 실행 대기가 포함될 수 있고, outside_server만으로 DDS·ROS·클라이언트 중 하나를 지목할 수 없습니다. 서로 다른 요청의 구간별 p99를 더하면 안 됩니다.

원본 203ms 실행과 연결하려면 그때의 명령·터미널 출력·원장 경로·동시 실행 노드를 확보하고 같은 조건에서 비교해야 합니다. 운영 모드의 별도 권한 잠금, 실제 D4 및 Gazebo 전체 연결은 이번 결과로 검증했다고 볼 수 없습니다.
