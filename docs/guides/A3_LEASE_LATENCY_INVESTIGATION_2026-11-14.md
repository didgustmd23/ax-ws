# A3 lease 지연 원인 조사 — 2026-11-14

## 판정

**과거 p99 초과의 원인은 아직 확정하지 못했으며 운영 지연 수정 완료가 아니다.**
검사한 8회차·8000개 요청은 모두 기존 기준을 통과했다. 저장소가 잠금 대기와 커밋 지연에
영향을 주는 것은 통제 비교로 확인했지만, 이것을 과거 실패의 유일한 원인으로 단정하지 않는다.
이번 변경은 내 시험의 상세 계측·다회차 실행·안전한 저장소 비교 기능이다. 다른 담당자 소스와
운영 권한 판정·원장 내구성·서비스 계약·실행기 기본 설정은 바꾸지 않았다.

## 찾은 과거 근거와 부족한 정보

- 이미지: p99 0.1095초, 기준 0.1초 초과.
- 별도 W1 기록: p99 0.116410921초, 서버 p99 0.098776528초.
  [기존 검증 문서](../evidence/w1_a4_b4/W1_A4_B4_VERIFICATION_2026-11-13.md) 참고.
- 둘을 같은 회차라고 합치지 않는다. 당시 원본 상세 출력·원장 경로·동시 노드 부하 정보가 없어
  현재 환경을 정확히 재현했다고 주장할 수 없다.

## 측정한 경로

클라이언트 송신 → ROS/실행기 대기 → checker.check → 원장 잠금 대기 → BEGIN → 조회 → 쓰기
→ COMMIT → 서버 반환 → 응답 수신·클라이언트 깨움으로 나눴다.

`a3_latency_profile.py`는 같은 request_id로 클라이언트 왕복과 서버 구간을 결합한다.
잠금과 DB는 원래 객체에 그대로 위임하며 SQL·판정·응답을 대체하지 않는다.
서버 밖 잔여 시간은 ROS 전송·실행기 진입·응답 전달·클라이언트 깨움 등의 합이다.
서버 안 잔여 시간에는 Python 계산·권한 잠금·스케줄링 영향 등이 포함될 수 있다.
어느 잔여 구간도 하나의 원인으로 단정하지 않는다. 구간별 p99끼리 더하면 전체 p99가 되지 않는다.
계측 오버헤드가 있어 원래 비계측 시험 결과와도 구분한다.

## 동일하게 유지한 조건

- local_task_executor, dev_allow, 모의 Action 지속 부하, 클라이언트 4개, 실행기 스레드 4개.
- 매 회차 새 command_id ACCEPT 1000개, 수락 기록 1000개 확인.
- p99 < 0.1초, 최대 < 0.5초 기준 유지. 무응답·실패는 시험 통과가 아니다.
- SQLite WAL + synchronous=FULL. 응답 전 수락 기록 저장을 생략하지 않음.
- 원래 시험에 배정된 A3 138~140 범위를 공용 도우미로 잠금 예약.
- CPU 부하는 시험 프로세스 집합에만 적용하고 종료 때 정리. 다른 노드 설정·코드는 변경하지 않음.

| 조건 | 회차 | p99 | 최대 | 해석 |
|---|---:|---:|---:|---|

| Linux 임시 원장 | 2 | 26.006ms | 30.165ms | 통과 |
| Windows 작업공간 원장, 최종 통제 비교 | 1 | 65.935ms | 79.282ms | 통과, Linux보다 지연 증가 |
| Windows 작업공간 원장, 최종 통제 비교 | 2 | 61.047ms | 75.062ms | 통과, Linux보다 지연 증가 |
| Windows 원장 초기 탐색 | 1·2 | 68.835 / 69.014ms | 93.012 / 80.598ms | 참고 자료 |
| Windows 원장 + 자기 CPU 2개 경합 초기 탐색 | 1·2 | 72.352 / 74.516ms | 91.401 / 103.206ms | 참고 자료, 두 CPU에 affinity 제한 |

초기 탐색은 TMPDIR을 바꿔 원장 위치를 지정했다. 이후 TMPDIR이 공용 domain 잠금 위치에도
영향을 줄 수 있음을 확인해 **AX_A3_LEDGER_TEMP_ROOT로 원장 위치만 바꾸도록 시험 도구를 고쳤다.**
최종 비교는 이 수정 후 결과를 사용한다. 이 시험 도구 수정은 과거 운영 지연의 수정이 아니다.

Linux 원장의 잠금 대기 p99는 약 17~21ms였다. 느린 저장소에서는 앞 요청의 커밋을 기다리는
시간이 병렬 요청에 누적된다. 이는 확인된 지연 기여 요인이지만 과거 109.5ms 초과 원인 확정은 아니다.

원본 JSON에서 만든 [분석 요약](../evidence/kim_validation_2026-11-14/lease_latency_investigation.json)에
각 회차의 단계별 분위수와 느린 요청 5개의 구간을 함께 저장했다. 모든 개별 요청과 pytest 로그는
개인 docs/reports/a3_latency_investigation 아래에 보관하며 기본 업로드 대상에서 제외한다.

## 재측정 방법

ROS 환경을 source한 작업공간에서 실행한다. 실제 로봇을 구동하지 않는다.

```bash
python3 tools/tests/run_a3_latency_profile.py \
  --output docs/reports/a3_latency_investigation/linux_recheck --rounds 2
python3 tools/tests/run_a3_latency_profile.py \
  --output docs/reports/a3_latency_investigation/storage_recheck \
  --temp-root .latency-scratch --rounds 2
```

같은 회차의 summary.json, profile.json, samples.json, pytest.log가 남는다. 실행 명령과 시점도
함께 기록한다. 테스트 밖 운영 노드를 dev_allow로 전환하거나 CPU 부하를 실제 운용과 섞지 않는다.
운영 원장은 기본 Linux ROS_HOME에 두는 것이 지연 측면에서 유리했다. 기존 원장을 이동할 때는
실행을 중단하고 SQLite 백업·복원 및 멱등 기록 보존을 검토해야 하며 자동으로 경로를 바꾸지 않는다.
